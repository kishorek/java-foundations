Method Overriding

Stage 5 Concept ⏱ 12 min 📖 Glossary

Same signature, NEW behavior: the child tailors the hand-me-down to fit. @Override is the tag proving the alteration was intentional — not an accident.

🔎 Motivating questionWhen does a child cook the family curry differently — and announce it?

Objectives

  • Override with @Override
  • Tell overload from override
  • Use dynamic dispatch simply

Needs first: Inheritance

1 Start with an analogy

Real life first, code second.

The tailor shop. Parent jacket speak() says “...”. Child Dog re-cuts the SAME jacket to “Woof!”. The @Override tag stitched on says “yes, deliberate alteration”. (Same name with DIFFERENT inputs is overloading — a different shop across the street.)

⚠️ Where the analogy breaksWhere it breaks: tailoring needs IDENTICAL measurements (signature). Change the inputs and you have sewn a NEW garment (overload) while the old one still hangs there — the classic “why is my override ignored?!”

2 The concept, plainly

One idea at a time, words before jargon.

Override = same name plus same parameter types plus compatible return, new body. Tag it @Override so typos become compile errors instead of silent new methods.

At runtime the OBJECT’s version runs, not the reference’s — Animal a = new Dog(); a.speak() barks. This dynamic dispatch powers all polymorphism.

Overload = same name, DIFFERENT inputs, chosen at COMPILE time. Override vs overload differ in every column: timing, rules, purpose. Keep them surgically apart.

Rules: cannot weaken access (public stays public); static and private methods do NOT override (they hide or stay put); final methods forbid overriding entirely.

⚙️ Tech details — precise facts
  • @Override is compiler-checked documentation: wrong signature plus tag = instant error. Always tag. No exceptions.
  • An override may return a SUBTYPE (Dog instead of Animal) — narrowing the promise is safe. This is called a covariant return.
  • super.speak() inside the override calls the PARENT version — for extending behavior (“parent thing, plus mine”) rather than replacing it.

3 Watch it move: Tailor shop

Step at your pace. Text explains every move.

4 Live code demo

Small, correct Java 17 (LTS) code. Read, trace, copy.

Main.javaJava 17
class Animal {
  void speak() { System.out.println("..."); }
}
class Dog extends Animal {
  @Override
  void speak() { System.out.println("Woof!"); } // tailored
}
Animal a = new Dog(); // reference Animal, object Dog
a.speak(); // "Woof!" — the OBJECT decides
▶ Output Woof!
  • Identical signature, brand-new body.
  • @Override guards against typo-ghosts.
  • Object type (Dog) beats reference type (Animal).
🔍 Illustrated fragmentKey lines showing the idea — a simplified simulation for learning, not a whole runnable file. Full programs appear in early lessons; here the concept is the star.
💡 Why this output?Dynamic dispatch: at runtime the JVM follows the OBJECT to Dog.speak, ignoring the reference’s quieter version.

6 Common mistakes (at least 3)

Wrong, why, fixed — learn from realistic slips.

❌ Mistake 1: void speak(String s) claimed as “override”.Why: Different inputs = OVERLOAD — a new method; the parent one still runs polymorphically.
✅ Fix: Match name plus inputs plus return exactly for a true override.
❌ Mistake 2: Typo speek() with no @Override tag.Why: Silent brand-new method; the parent version keeps running; confusion for weeks.
✅ Fix: @Override on EVERY override — typos detonate at compile time.
❌ Mistake 3: Shrinking public to private in the child.Why: Illegal weakening — callers promised public get locked doors.
✅ Fix: Keep access, or widen it. Never narrow.

9 Takeaways + next step

  • Override = same shape, new behavior.
  • @Override always — no exceptions.
  • Object type wins at runtime.
  • Overload is not override, in every column.
