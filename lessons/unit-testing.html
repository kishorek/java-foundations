Basic Unit Testing

Stage 6 Practice ⏱ 16 min 📖 Glossary

Unit tests are robot taste-testers: feed known inputs, compare expected versus actual. Green means safe to refactor; red names the exact betrayal.

🔎 Motivating questionWhy do chefs taste with a spoon instead of serving blindly?

Objectives

  • Write a JUnit test
  • Compare expected vs actual
  • Explain why tests help

Needs first: File Reading and Writing

1 Start with an analogy

Real life first, code second.

The taste spoon. Recipe add(2,3) MUST taste 5. @Test writes the spoon; assertEquals(expected, actual) sips. Red spoon → fix the RECIPE, never blame the spoon.

⚠️ Where the analogy breaksWhere it breaks: spoons test single dishes, never whole banquets. 100% passing spoons still miss integration bugs — also test edges (0, negatives, empties) and a few journeys end to end.

2 The concept, plainly

One idea at a time, words before jargon.

Shape: @Test void adds() { assertEquals(5, add(2, 3)); } with JUnit 5. Import the Assertions statically; name tests like sentences (rejectsNegativeAge).

Order is EXPECTED first, actual second: assertEquals(5, add(2,3)). Swapped order still works but prints confusing failure messages.

Run via IDE green-button or mvn test; red output reads “expected 5 but was 4” plus the exact line. Fix code, never edit the test to match bugs.

Test EDGES, not just sunshine: 0, negatives, empties, nulls. Bugs breed at boundaries — the middle usually behaves.

⚙️ Tech details — precise facts
  • JUnit 5 (Jupiter): @Test, @BeforeEach setup, assertEquals / assertTrue / assertThrows — the working vocabulary.
  • assertThrows(IllegalArgumentException.class, () -> ...) tests FAILURE paths — guards deserve tests too.
  • Tests are executable SPECIFICATIONS: read them to learn what code promises. Write them for Main’s helpers in the capstone.

3 Watch it move: Taste spoons

Step at your pace. Text explains every move.

4 Live code demo

Small, correct Java 17 (LTS) code. Read, trace, copy.

Main.javaJava 17
// Calculator.java: the recipe
static int add(int a, int b) { return a + b; }
// CalculatorTest.java: the spoons
import static org.junit.jupiter.api.Assertions.*;
import org.junit.jupiter.api.Test;
class CalculatorTest {
  @Test void adds() { assertEquals(5, add(2, 3)); }
  @Test void zeroEdge() { assertEquals(3, add(3, 0)); }
  @Test void negatives() { assertEquals(0, add(-2, 2)); }
}
▶ Output 3 tests, all green.
  • Two files: recipe plus spoons.
  • Expected first, actual second — always.
  • Sunshine plus edges: zero and negatives.

6 Common mistakes (at least 3)

Wrong, why, fixed — learn from realistic slips.

❌ Mistake 1: assertEquals(actual, expected) — swapped.Why: Works, but failure messages read backwards.
✅ Fix: Expected FIRST, actual second. Always.
❌ Mistake 2: Sunshine-only tests (happy paths).Why: Edges harbor the bugs; middles behave.
✅ Fix: Add 0, empty, negative, null-adjacent cases.
❌ Mistake 3: Testing by eyeballing prints, not asserts.Why: Humans must stare every run; robots judge instantly.
✅ Fix: Assert; let the machine deliver verdicts.
❌ Mistake 4: Editing the TEST to match buggy code.Why: Shooting the taste-spoon for reporting poison.
✅ Fix: Red means fix the RECIPE.
