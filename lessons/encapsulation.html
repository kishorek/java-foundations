Encapsulation

Stage 5 Concept ⏱ 14 min 📖 Glossary

Hide the engine, show the steering wheel. Private fields plus public methods keep objects VALID even when callers are careless, rushed, or malicious.

🔎 Motivating questionWhy can’t bank customers open the vault, yet anyone may use the ATM?

Objectives

  • Make fields private
  • Write getters/setters
  • Validate inside setters

Needs first: The this Keyword

1 Start with an analogy

Real life first, code second.

The child-proof medicine bottle: locked cap (private) + measured spoon (public method). Direct handfuls are impossible; safe measured doses are easy. The rules live in ONE place.

⚠️ Where the analogy breaksWhere it breaks: caps annoy careful adults too. Encapsulation demands WELL-DESIGNED methods — clumsy APIs make users pry the cap off (or duplicate the logic outside). Design the spoon lovingly.

2 The concept, plainly

One idea at a time, words before jargon.

Make fields private; expose public getters/setters: getPages(), setPages(n). The setter VALIDATES — rejecting negatives, clamping ranges — so ONE guard protects EVERY caller.

Expose BEHAVIOR, not raw flags: borrow() (which checks limits) beats setBorrowed(true) (which checks nothing). Methods carry rules; naked setters carry none.

Read-only = getter with NO setter (title readable, unchangeable). Write-only is rare — question it when tempted.

Validation errors should speak loudly: throw with a message naming the rule. Silent ignoring ("if valid, store; else shrug") hides bugs for months.

⚙️ Tech details — precise facts
  • private = this class only. The compiler REJECTS outside touches — the guardrail is mechanical, not social.
  • Getters returning MUTABLE objects (lists, dates) leak the insides: callers mutate your privates. Return copies or unmodifiable views.
  • Java 16+ records (record Book(String title)) auto-give private-final fields plus getters — encapsulation pre-packed for simple data carriers.

3 Watch it move: Vault plus ATM

Step at your pace. Text explains every move.

4 Live code demo

Small, correct Java 17 (LTS) code. Read, trace, copy.

Main.javaJava 17
class Book {
  private int pages; // hidden vault
  public int getPages() { return pages; }
  public void setPages(int p) {
    if (p <= 0) throw new IllegalArgumentException("pages must be > 0");
    pages = p;
  }
}
Book b = new Book();
b.setPages(-5);  // rejected loudly
b.setPages(200); // accepted
b.getPages();    // 200
▶ Output Exception on minus 5; then 200 accepted and reported.
  • pages is unreachable from outside.
  • Minus 5 detonates with a clear message.
  • 200 stores; the getter reports it.

6 Common mistakes (at least 3)

Wrong, why, fixed — learn from realistic slips.

❌ Mistake 1: public int pages; — anyone sets minus 5.Why: No doorway, no guard. Corruption needs exactly one careless line.
✅ Fix: private plus a validating setter.
❌ Mistake 2: A setter with zero checks.Why: A pointless wrapper — all ceremony, no protection.
✅ Fix: Validate inside: reject non-positive with a clear error.
❌ Mistake 3: getList() returning the live private list.Why: Callers clear() your insides directly — encapsulation theater.
✅ Fix: Return a copy or an unmodifiable view.

9 Takeaways + next step

  • Hide fields; expose safe actions.
  • Validate once, inside, loudly.
  • Read-only = getter without setter.
  • Never leak mutable insides.
