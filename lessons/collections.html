Collections: List, Set, Map

Stage 6 Concept ⏱ 16 min 📖 Glossary

Arrays are fixed trays; collections are SMART shelves. Lists keep ORDER, Sets ban DUPLICATES, Maps find by KEY. Three tools, three promises, zero confusion after this lesson.

🔎 Motivating questionWhen do you need a queue, a guest-list, or a labeled coat shelf?

Objectives

  • Pick List/Set/Map
  • Explain order vs unique
  • Sketch key-value use

Needs first: Common Exceptions & Defensive Code

1 Start with an analogy

Real life first, code second.

Party tools. List = photo queue (ordered, duplicates fine). Set = VIP guest list (each name once). Map = coat-check tickets (ticket finds coat instantly).

⚠️ Where the analogy breaksWhere it breaks: coat tickets cost machinery (hashing, memory). Storing three fixed scores? The humble array wins — smart shelves earn their keep at scale and change.

2 The concept, plainly

One idea at a time, words before jargon.

List: ordered, indexed with get(2), duplicates welcome. Set: unique only, NO index, NO order promise. Map: key to value pairs, keys unique, values may repeat.

Code to INTERFACES: List team = new ArrayList<>(); — swap ArrayList for another List later without touching callers. Concrete-left is lock-in.

For YOUR objects, equals and hashCode decide uniqueness and key matching. Defaults use identity: twins count as strangers until you override both together.

Map views: keySet() (tickets), values() (coats), entrySet() (pairs). Loop entrySet to visit both sides at once.

⚙️ Tech details — precise facts
  • HashSet and HashMap order is unspecified AND unstable across runs — never rely on it; Linked variants preserve insertion order.
  • Set and Map hashing needs consistent equals plus hashCode: equal objects MUST share hash codes, or lookups silently miss.
  • Big-O feel: ArrayList get is instant, contains scans; HashMap get is near-instant. Structure choice IS performance choice.

4 Live code demo

Small, correct Java 17 (LTS) code. Read, trace, copy.

Main.javaJava 17
import java.util.List;
import java.util.Map;
import java.util.Set;
List<String> queue = List.of("Ada", "Bob", "Ada"); // dupes kept
Set<String> guests = Set.of("Ada", "Bob");        // dupes refused
Map<String, Integer> age = Map.of("Ada", 18);     // ticket to coat
// queue.size()=3  guests.size()=2  age.get("Ada")=18
▶ Output queue=3, guests=2, Ada=18.
  • The List keeps both Adas in order.
  • The Set admits each name once.
  • The Map finds 18 by ticket "Ada".

6 Common mistakes (at least 3)

Wrong, why, fixed — learn from realistic slips.

❌ Mistake 1: Set expected to keep insertion order or indexes.Why: No index exists, no order promised — get(0) does not even compile.
✅ Fix: Order plus index needs List. Uniqueness needs Set.
❌ Mistake 2: Map with duplicate keys expecting both kept.Why: Keys are unique: the second put REPLACES the first, silently.
✅ Fix: Check containsKey first when replacement matters.
❌ Mistake 3: ArrayList<String> team = ... everywhere (concrete left).Why: Locked to one implementation — swapping costs touch-everywhere.
✅ Fix: List<String> team = new ArrayList<>(); — interface left.

9 Takeaways + next step

  • List = order, Set = unique, Map = keyed.
  • Program to interfaces, not implementations.
  • Keys unique; values may repeat.
  • Hash order is not a promise.
