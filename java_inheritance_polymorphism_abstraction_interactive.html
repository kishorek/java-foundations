THE BIG PICTURE

1. Why do we need these three ideas?

In the previous lesson, you learned that a class is a blueprint and an object is an instance. Now imagine an app with dogs, cats, birds, and fish. They all have some things in common, but they do not all behave in the same way.

Analogy: a family of vehicles
A car, bus, and motorcycle are all vehicles, so they share ideas like speed or a registration number. But they may start, stop, and carry passengers differently. Java gives us ways to represent what is shared and what is specialised.

Inheritance

Reuse and specialise features from a parent class.

“A Dog is an Animal.”

Polymorphism

Use one common type, while each actual object behaves in its own way.

“Make every animal speak.”

Abstraction

Expose the essential operation and hide unnecessary implementation details.

“Press start; don't manage the engine internals.”

How they relate

Inheritance can create a family of related types; overriding enables different behaviours; abstract classes and interfaces define contracts.

Simple memory aid: Inheritance = “is a kind of”; polymorphism = “same request, different response”; abstraction = “show what matters, hide how it works.”
CONCEPT 1

2. Inheritance: build on an existing class

Inheritance lets a new class reuse accessible fields and methods from an existing class. The existing class is often called the parent or superclass; the new class is the child or subclass.

class Animal {
    void eat() {
        System.out.println("This animal eats.");
    }
}

class Dog extends Animal {
    void bark() {
        System.out.println("Woof!");
    }
}

Dog dog = new Dog();
dog.eat();  // inherited from Animal
dog.bark(); // defined in Dog
Analogy: a starter kit
The parent class is a starter kit with useful shared features. The child class gets those accessible features and adds its own. A Dog can eat because it inherits eat(), and bark because Dog defines bark().

Read the keyword extends

  • class Dog extends Animal declares that Dog is a specialised kind of Animal.
  • Dog can use accessible inherited members such as the public or protected methods shown here.
  • Dog can add its own methods or override inherited methods.

Inheritance is not copying and pasting

Inheritance creates a type relationship. You do not manually duplicate the parent's code into the child class. Each Dog object is still one Dog object, with inherited behaviour available through the class relationship.

Important: a subclass does not directly access a parent's private fields. The parent can expose suitable methods to work with its private state. Constructors are not inherited either; a subclass constructor calls a superclass constructor.

Calling the parent constructor with super

class Animal {
    String name;

    Animal(String name) {
        this.name = name;
    }
}

class Dog extends Animal {
    Dog(String name) {
        super(name); // initialise the Animal part
    }
}

super(name) calls the matching superclass constructor. In Java, a call to super(...) must be the first statement in a constructor when written explicitly.

CUSTOMISE BEHAVIOUR

3. Method overriding vs method overloading

A subclass may want to use a method name it inherited, but provide its own behaviour. That is overriding.

class Animal {
    void speak() {
        System.out.println("Some animal sound");
    }
}

class Dog extends Animal {
    @Override
    void speak() {
        System.out.println("Woof!");
    }
}

The @Override annotation tells Java that you intend to override an inherited method. The compiler can catch mistakes such as misspelling the method name or using an incompatible signature.

Analogy: the same question in different households
If you ask “What sound do you make?” the dog answers “Woof!” and the cat answers “Meow!” They respond to the same kind of request with their own specialised behaviour.

Overloading is different

class Printer {
    void print(String text) { }
    void print(int number) { }
    void print(String text, int copies) { }
}

Overloading means the same method name has different parameter lists. The compiler chooses which overload fits the arguments. Overriding means a subclass supplies a new implementation of an inherited method.

OverloadingOverriding
Where?Often in the same classSubclass and superclass relationship
ParametersMust differ in number, type, or orderMust match the inherited method signature
PurposeSimilar action for different inputsSpecialised behaviour for a subtype
Typical selectionCompile timeRuntime for overridden instance methods
Memory trick: overloading = same name, different inputs. Overriding = same inherited method, new implementation.
CONCEPT 2

4. Polymorphism: one request, many behaviours

The word sounds intimidating, but the idea is simple. A variable declared as a parent type can refer to an object of a child type. When you call an overridden instance method, Java runs the implementation belonging to the actual object.

Animal first = new Dog();
Animal second = new Cat();

first.speak();  // Woof!
second.speak(); // Meow!

Both variables are declared as Animal. But the objects created are a Dog and a Cat. The actual object determines which overridden speak() method runs.

Analogy: a universal remote
The remote has a common “power” button. Pressing it on a TV turns on the TV; pressing it on a speaker turns on the speaker. You use one kind of command without needing to know every device's internal details.

Polymorphism becomes powerful with loops

Animal[] animals = {
    new Dog(),
    new Cat(),
    new Bird()
};

for (Animal animal : animals) {
    animal.speak();
}

The loop does not need a separate if statement for each animal. Each object supplies its own behaviour through the shared method.

Important distinction: the compiler checks what methods are available through the declared type, Animal. At runtime, Java chooses the overridden implementation for the actual object. A parent-typed variable cannot directly call a child-only method unless you use an appropriate design or cast safely.

CONCEPT 3A

6. Abstract classes: a useful base that is not complete by itself

Sometimes you want to define what all related objects have in common, but the base class cannot sensibly implement every behaviour. Java lets you declare an abstract class.

abstract class Shape {
    abstract double area();

    void describe() {
        System.out.println("I am a shape.");
    }
}

class Circle extends Shape {
    private double radius;

    Circle(double radius) {
        this.radius = radius;
    }

    @Override
    double area() {
        return Math.PI * radius * radius;
    }
}
Analogy: a shape worksheet
The worksheet says every shape should be able to report its area, but the formula depends on the shape. A circle uses π × radius²; a rectangle uses width × height. The abstract parent sets the expectation, and each concrete child supplies the formula.
  • An abstract class cannot be instantiated directly with new Shape().
  • It can contain both abstract methods (no body) and concrete methods (with a body).
  • A concrete subclass must implement inherited abstract methods unless that subclass is also abstract.
  • An abstract class can have fields and constructors, which run as part of subclass construction.
Use an abstract class when: related classes share common state or implemented behaviour, and some behaviour must be supplied by each specific subclass.
CONCEPT 3B

7. Interfaces: agree on a capability

An interface describes a contract: a set of operations that a class promises to provide. It is especially useful when different kinds of classes should support the same capability, even if they are not the same kind of thing.

interface Payable {
    void pay(double amount);
}

class CardPayment implements Payable {
    @Override
    public void pay(double amount) {
        System.out.println("Paid by card: " + amount);
    }
}

class WalletPayment implements Payable {
    @Override
    public void pay(double amount) {
        System.out.println("Paid by wallet: " + amount);
    }
}
Analogy: a charging socket standard
A socket defines what connection a compatible device must support. The device internals can be different, but they agree on the interface. Similarly, code can call pay() on any Payable implementation.

Use the interface polymorphically

Payable payment = new CardPayment();
payment.pay(250.00);

Payable another = new WalletPayment();
another.pay(125.00);

Both objects satisfy the Payable contract. The caller can depend on the interface rather than hard-coding one payment class.

Abstract class or interface?

Abstract classInterface
Useful for a related family sharing state and implementation.Useful for defining a capability or contract across potentially unrelated classes.
A class can extend only one class.A class can implement multiple interfaces.
Can have instance fields and constructors.Cannot be instantiated; fields declared in interfaces are implicitly public, static, and final. Interfaces can have abstract, default, static, and private methods under Java's rules.
Beginner rule of thumb: choose an abstract class for a shared foundation; choose an interface for a capability that different classes can promise to provide. They can also be used together.
PUT THE IDEAS TOGETHER

8. One scenario, three ideas

Imagine a delivery app with different delivery methods.

Inheritance

BikeDelivery and VanDelivery extend a shared Delivery class for common data such as a delivery ID.

Polymorphism

Both provide their own estimateTime(). The app calls that method on a Delivery reference.

Abstraction

The app depends on a simple operation like deliver(), without needing to know every internal routing step.

Interface option

An interface such as Trackable could be implemented by a delivery, a parcel locker, or another trackable item.

abstract class Delivery {
    abstract int estimateTime();
}

class BikeDelivery extends Delivery {
    @Override int estimateTime() { return 25; }
}

class VanDelivery extends Delivery {
    @Override int estimateTime() { return 40; }
}

Delivery job = new BikeDelivery();
System.out.println(job.estimateTime()); // 25

The declared type, Delivery, tells the compiler which operation is available. The actual object, BikeDelivery, determines the overridden implementation at runtime.

GOOD DESIGN

9. Design rules and common mistakes

  • Use inheritance for a genuine “is-a” relationship. A Dog is an Animal. A Car is a Vehicle. A Car is not an Engine; it has an Engine, which is a different relationship.
  • Prefer composition when one thing has another thing. “Car has an Engine” is usually better modelled by a field that refers to an Engine object.
  • Use @Override. It helps the compiler catch accidental signature mistakes.
  • Depend on abstractions when useful. Accepting an interface type can make code work with several implementations.
  • Do not force every difference into inheritance. Deep, complicated class hierarchies are difficult to change. Use the simplest design that expresses the domain.
Analogy: is-a vs has-a
A Labrador is an Animal, so inheritance may fit. A Car has an Engine, so composition fits. If you say “Car extends Engine,” the model is probably wrong: a car is not a kind of engine.
Frequent beginner mistakes: trying to instantiate an abstract class; forgetting to implement an abstract method; assuming private parent fields are directly accessible; confusing overloading with overriding; or assuming the variable's declared type always determines which overridden method runs.
PRACTICE

10. Practice problems

Try each question before revealing the explanation.

1. In class Dog extends Animal, which is the parent class?

Animal is the parent/superclass; Dog is the child/subclass.

2. Is “a Bicycle is a Vehicle” a plausible inheritance relationship?

Yes. A bicycle is a kind of vehicle, so Bicycle extends Vehicle may be sensible if the shared model fits.

3. What is the difference between overloading and overriding?

Overloading uses the same method name with different parameter lists. Overriding replaces inherited instance-method behaviour in a subclass using a matching signature.

4. What prints if Animal a = new Dog(); and Dog overrides speak(), then a.speak() is called?

Dog's implementation runs, because overridden instance methods use runtime dispatch based on the actual object.

5. Can you write new Shape() if Shape is abstract?

No. Abstract classes cannot be instantiated directly. Create an instance of a concrete subclass such as Circle.

6. When might an interface be better than an abstract class?

When different classes need to promise the same capability without necessarily sharing a common parent class or common instance state.

7. A Car has an Engine. Is that usually inheritance or composition?

Composition. A car has an engine; it is not a kind of engine.

8. Why add @Override above a method?

It documents the intent and asks the compiler to verify that the method actually overrides an inherited method.
